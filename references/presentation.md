# 展示与文风

首屏回答：给谁用、解决什么重复劳动、怎样开始。采用「中文品牌名 · English Name」时保持 repository slug 简短可检索；英文名表达用途，中文名表达记忆点。新项目给出 3 个有理由的候选并推荐一个，用户已经委托自主命名时直接采用推荐项。不要擅自重命名既有远程仓库。

一句话简介公式：目标用户 + 可验证动作 + 具体收益。例：「让 AI 按你的文风维护 GitHub 文档，保留变更依据与真实测试记录。」不用革命性、最强、全自动等无证据承诺。

默认新 README 顺序：品牌与定位 → 痛点/适用人群 → 最短上手 → 能力与边界 → 实际示例 → 测试 → 更新/贡献/许可。已有仓库沿用原顺序；目录只在篇幅需要时添加。

| 类型 | 读者首先需要 |
|---|---|
| Skill | 安装位置、调用例子、工具权限和兼容性验证状态 |
| 应用/网页 | 界面或演示、启动方式、配置、部署边界 |
| CLI/工具 | 最短可运行命令、输入输出、依赖 |
| 游戏 | 玩法、运行平台、启动方式和素材许可 |

Topics 选择实际领域、产物类型和关键工作流，例如 agent-skills、documentation、readme、changelog。只列项目确实相关的词，不为流量堆热门品牌。核对现有 Topics，更新时保留仍相关的项。About 简洁；主页 URL 只有真实存在才填写。徽章必须指向真实许可证、工作流或发布版本，不能用静态绿色徽章伪装测试通过。

参考仓库时学信息层次而不是复制宣传。提取偏好后记录来源 URL、提取日期、适用范围。发现参考文档中技能数、目录标题或版本数字不一致，不继承这些错误。
